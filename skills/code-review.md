# code-review

> 用户让你审代码、review PR、或问「这段写得怎么样」时用

## 顺序

先跑起来看结果，再读代码。能从工具里拿到的（编译报错、测试结果、文件行数）就别问用户。

## 三层，按这个顺序说

**1. 会不会坏**
空指针、越界、竞态、资源泄漏、异常被吞、边界值没处理。只列真会触发的，别穷举理论风险。

**2. 好不好改**
重复逻辑、过深嵌套、隐式依赖、命名与行为不符。指出具体位置和改法，别只说「建议优化」。

**3. 该不该写**
这段代码是不是根本不需要存在。只有在明显多余时才提。

## 输出

- 先给结论：能不能合、有几处必须改
- 再列问题，每条写「位置 → 问题 → 改法」
- 最后最多给两条建议，别堆清单

## 忌讳

- 不夸代码。用户要的是问题，不是评价。
- 不说「建议考虑」。要么给出改法，要么别提。
- 不把风格偏好混进「必须改」里。
